Field Lessons & the Sync Contract

What the Zazi iZandi field test taught us the hard way — and an honest, from-scratch verdict on masi-app's offline-sync architecture before it meets the field.

Date 2026-07-04 Compared zazi-izandi-app ⇄ masi-app Method docs + code + migration audit, file:line-verified Author Claude (Fable 5) for Jim McKeown
The short version

Masi's sync core is genuinely better than Zazi iZandi's — in three places it already implements fixes ZZ still has on its deferred list. Built from scratch, I would keep this architecture: atomic outbox, compare-and-swap finalization, single-writer SQLite, deterministic IDs. But masi is missing four specific defenses for failure modes ZZ actually hit in the field — and every one is a "quiet data quarantine," not a crash. All four are bounded fixes, not architecture surgery.

Keep: the engine. Outbox, CAS finalization, writer/reader split, deterministic IDs, contract-as-tests. This is the strongest version of this design across both codebases.
Fix before launch: auth-gate on sync · pull-side pending-local-wins · offline cold-start login · the ten server unique indexes onConflict:'id' can't arbitrate.

The master mental model

Across all of ZZ's field data, the sync pipeline almost never failed. What failed were the preconditions the pipeline trusts: a live auth session, server constraints the conflict-arbiter can see, a pull that tells the local store the truth, a login gate that lets an offline user in. Every finding below is a missing precondition-guard — which is why every fix is bounded.

Pull-side pending-local-wins — masi has ZZ's F7 bug, in the same code shape
ZZ F7 · 🔴 blocker · their #1 user-facing complaint: "groups vanished / appeared the next day / never"

This one startled me. Masi's ChildrenContext.mergeServerRows src/context/ChildrenContext.js:10–20 is the exact pre-fix logic ZZ root-caused: a local row survives the pull only if it's unsynced and its id is absent from the server — so a pending edit to an already-synced row gets clobbered. And that merge only shapes React state; saveRows(pulled.children, storage.saveChild) ChildrenContext.js:107–127 then writes every server row into SQLite through repositories that do blind upserts with no pending guard childrenRepository.js:318–331.

EA edits a child offline
(sync_status = pending)→ app pulls from server
(row id already exists)→ stale server row overwrites the local edit, marked "synced"→ the EA watches their work revert on-screen
Why it's narrower hereMasi's atomic outbox still holds the edit's payload, so the push usually lands later and self-corrects — where ZZ's flag-derived outbox lost the pending intent entirely. But two harms remain: the visible UI revert (the trust-killer that generated ZZ's facilitator escalation), and a real loss window — a second edit rebuilds its payload from the clobbered row, and because outbox ids are table:record:operation, update #2 replaces update #1's payload. First edit: permanently reverted.
The portBring ZZ's arbiter-aware mergeServerRows.js semantics into masi's SQLite write path, not just the state merge: a pull must never overwrite a row whose sync_status ≠ 'synced'.
Mental model · pending-local-wins

Offline-first has exactly one sacred invariant on the pull side: the server is authoritative for everything except what the device hasn't told it yet. A pending local row is a promise in transit — until it's acknowledged, the pull must treat it as more true than the server. "Server has this id" is the wrong test; "device has unacknowledged intent for this row" is the right one.

4
Ten server unique indexes that onConflict: 'id' cannot arbitrate
ZZ F1 / F8 / F9 family · 🔴 · the dominant field failure — 23505 duplicate-key → TERMINAL → dependency cascade
client mints a NEW id for a logical row that already exists server-side→ PK doesn't match → INSERT attempted→ secondary UNIQUE fires: 23505→ TERMINAL→ dependency skip poisons child tables every cycle

On one ZZ device this exact chain skipped membership sync on 101 of 101 cycles for ~9 hours. The EA saw only: "sync failed."

A migration audit of supabase/migrations/ found the exposure on: the three assignment tables' active-pair partial indexes, child_programme_enrollments, child_class_memberships (keyed on child + academic year, not class — moving a child without exiting the old membership collides), group_ea_assignments (bare group_id: at most one active EA per group), grouping_versions (×2), class_grouping_state (a one-row-per-class/year singleton with no deterministic id), and groups.display_number.

Why masi is more exposed than ZZMasi's repositories do deactivate-before-insert locally, and ignoreDuplicates protects the immutable-assignment inserts. But masi is more multi-writer than ZZ: the head-office grouping workflow assigns children to EAs centrally, so local and server disagreeing about "which row is active" is realistic — and Finding 2 can manufacture exactly that disagreement.
The fix menu, in order of preference① Extend the deterministic-id pattern already used for letter_mastery — which made its 23505 impossible by construction. ② Correct onConflict arbiters to match the real constraints. ③ ZZ's beforeUpsert server-reconciliation hook (their F9 fix) for tables where neither works.
Adjacent trapThe identity triggers raise 23514, which classifyError treats as retryable — an archive re-push whose created_at/assigned_at drifted would retry forever with backoff.
Mental model · deterministic identity

If a row's identity is really its logical key ("this child, in this group, in this grouping version"), then deriving the UUID from that key (UUIDv5) means every device, every install, every retry agrees on the id — and "insert the same thing twice" becomes an update instead of a collision. You eliminate the entire conflict class instead of arbitrating it. Masi already proved this pattern on three tables; this finding is about finishing the job.

The assessment render-performance pack
ZZ OTA 1.1.0+15 · measured tap-lag + countdown drift on Galaxy A03s-class devices

Masi's useAssessmentSession src/hooks/useAssessmentSession.js:57–69 is ZZ's pre-fix design: a tick-counting setInterval (elapsedRef += 1) that drifts when low-end Android throttles ticks, no monotonic clock, no AppState background-pause (backgrounding silently stops the clock — background time is free), a per-second state update re-rendering the whole capture screen, and no memoized grid tiles. Masi has more and longer assessments coming with the WelaPLUS battery, so exposure grows from here.

The portZZ's fix is a clean reference: monotonic performance.now() elapsed · an authoritative isExpired() hard-stop on every capture-mutation path · background-as-pause · an isolated 1 Hz countdown leaf component · React.memo tiles (26 → 1 repaints per tap). Masi already did the sibling fix — the ElapsedTime 1 Hz isolation (commit 3b5d507). This is the same medicine for the assessment seam.

Sync-status UX is a trust system — treat it like one
ZZ F2 · 🟠 "trust-destroying" · 124 of 125 sync cycles read "failed" on one device

On ZZ devices, one stuck table poisoned the overall success flag, so EAs concluded "the app never syncs" even while 12 records uploaded cleanly in the same cycle. That narrative — more than the underlying bug — did the reputational damage. Masi's result.success also flips false on any single failed record.

"Everything is saved on your phone — 3 items waiting for signal" and "2 items need attention" are different messages, and the field trusts you differently for each.

Server pull-query capacity as data grows
ZZ F4 · 🟠 · Postgres statement timeout 57014 on assessment_items — near-universal across devices

ZZ's assessment_items pull started timing out on nearly every device once real data volumes arrived. Good news from the audit: every masi pull-path foreign key is indexed. P2 · ProcessHabits worth stealing
8
Four operational habits from ZZ's remediation campaign
  • The version-gated startup repair hook. ZZ learned that shipping a fix doesn't help rows already quarantined on devices — they needed an allowlisted, once-per-upgrade requeueFrozen. Masi has no such mechanism; build the hook once and every future field fix can carry its own recovery.
  • Real-engine-first DB tests. The single most instructive ZZ datapoint: expanding their better-sqlite3 allowlist from 8 to 26 suites immediately surfaced a production bug (an FK cascade wiping pending state on pull) that 1,830 passing mock tests could not see — plus an earlier device-only crash hidden by "wish-shaped" mocks. Their landing rule is worth adopting: any suite that executes SQL runs on the real engine. Masi is at 13 real-engine suites.
  • OTA cohort discipline. ZZ stranded their 1.0.0 testers (OTAs can't cross a runtimeVersion), and once stranded iOS by building Android-only. Cheap rules: build both platforms every time, keep field fixes JS-only where possible, track which cohorts each release actually reaches.
  • The field-diagnostics loop. Export Logs → capture in an issue log separating observed evidence from interpretation → triage into root-cause families → one remediation plan. That workflow found everything above. Masi already has Export Logs / Export Database — the loop is ready to run.
9
Product signal from ZZ's EA surveys that transfers directly
  • "No photos" and fast clock-in/out are why EAs prefer ZZ over Teampact. Protect those properties in masi — they are competitive features, not gaps.
  • Sort orders must reflect grouping everywhere, or EAs conclude grouping "didn't work" (ZZ's alphabetical rosters made testers believe auto-grouping had failed).
  • The photo paradox is coming for masi too: 44/47 EAs said before/after photos "would help" accountability, while also citing the absence of photos as a top reason they prefer the app. Decide the accountability policy (photos vs. assessment-trail integrity) deliberately, before the field decides it for you.

Is masi's sync contract built right?

Verdict: yes at the core — and I mean that concretely, not politely. Masi's engine is the stronger of the two codebases in every structural dimension; ZZ's advantage is purely that it has been shot at in the field. A from-scratch rebuild would differ at the edges, not the center.

Why the lock-storm class simply can't happen here

This deserves its own picture, because it's the deepest structural difference — and it's the fix ZZ's own handoff document (sqlite-lock-storm-handoff-for-masi.md) called "Slice 2" and deferred. Masi already built it.

ZZ's model — the storm

🔒 WAL writer lock
txn conn #1#2#3…#954

expo-sqlite's withExclusiveTransactionAsync secretly opens a new native connection per transaction. Finalizing 954 records the per-record way spawned 954 throwaway connections fighting one writer lock — screens timed out with "database is locked" mid-lesson.

Masi's model — one writer, one reader

writer · mutex queue · BEGIN IMMEDIATE
reader · query_only · never blocks

One persistent writer behind a JS mutex src/db/client.js:94–135; all reads on a separate read-only connection. In WAL mode readers never wait on the writer — so screens stay responsive during a heavy sync. The failure class is absent by construction, not by tuning.

Two design calls I'd defend explicitly

Row-granularity last-write-wins is correct for this domain. The data is single-writer by construction — an EA owns her children, sessions, and assessments — so CRDTs or field-level merging would be complexity with no payoff. The assignment model is the conflict-avoidance mechanism; that deserves to be stated as a named invariant in the contract map rather than left implicit.

Skip PowerSync / WatermelonDB / ElectricSQL. ZZ ran this calculus and locked it until ~2,500 active users. Masi has now hand-built the hard parts (outbox, CAS, contract tests), so the payback is even weaker here.

Where a from-scratch build would differ

The pull side is the one subsystem I would not have built this way — it's a generation older than the push side. The push engine got the clean-slate rebuild; the pull is still context-level code: React-state merging in ChildrenContext, per-row saveRows loops, no arbiter awareness, no pending-local-wins, and no tombstone semantics (pulls filter to active rows, so absence can't be distinguished from deletion — a membership removed by head office never disappears from an EA's SQLite). From scratch: pulling is a repository concern — one applyServerRows(rows, { arbiter }) per table, pending-local-wins inside a single transaction, with ZZ's mergeServerRows.js as the field-validated reference. This is also where Finding 2 lives, so the fix and the redesign are the same work.

Relatedly, make the currently-implicit decision explicit: masi pulls only reference data plus child/group/membership scaffolding — sessions, assessments, and time entries are push-only, so a re-onboarded EA on a fresh device sees no history. That may be exactly right (the data is safe on the server; the dashboard is the history surface), but it should be a documented choice, not an accident of what got built.

Batching is narrower than it should be for field connectivity. Only four tables batch (BATCHABLE_UPSERT_TABLES); everything else is one PostgREST round trip per record, serialized. A 300-row regroup backlog on a school's flaky 4G is 300 sequential HTTP requests. With the single-writer design the local transaction cost is fine — the network round trips are the cost. Extending batching to memberships and enrollments is a contained change with an outsized field payoff.

The honest "would I do it differently" answer: the PostgREST-upsert-plus-RLS transport. The most complex artifact in the whole sync system — the contract map, the creator-SELECT fallback policies, the accepted advisor warnings, the upsert-visibility gotcha now documented in three places — exists only because the client writes through per-table upserts that RLS must authorize row-by-row mid-conflict-check. From scratch, I'd seriously weigh a single transactional ingest RPC: the outbox stays exactly as-is (offline behavior is a property of the outbox, not the transport — ZZ's "an RPC can't run offline" rejection conflates the two), but the client ships a batch of operations and one server function applies them in FK order, atomically, with authorization in one auditable place. That collapses PUSH_ORDER, the dependency-cascade skipping, and the visibility policies.

Recommendation, not a rewrite

I am not recommending a migration now — the current approach works, the tests tame it, and go-live is close. Hold the ingest RPC as the pressure-relief valve: WelaPLUS adds tables, and if the RLS contract map keeps compounding, that's the signal to pull it.

Small engine nits (performance, not correctness, thanks to the single writer): finalizeManySuccess runs three statements per record inside its chunk transactions where a bulk UPDATE/DELETE … WHERE id IN with a matched-count guard would do; and getReadyRecords' 1000-row cap leaves any remainder waiting for the next trigger — the 30-second status refresh covers it, but it deserves a comment.

The bottom line

The offline-sync failure point you're worried about has, in ZZ's field data, a very specific anatomy: it is almost never the push pipeline — it is the preconditions the pipeline trusts. A dead session. A server constraint the arbiter can't see. A pull that lies to the local store. An auth gate that bounces the user. Masi's engine core is the best version of this design across both codebases; the four P0 items are precisely the missing precondition-guards; all are bounded fixes; and ZZ has already paid the field-testing cost of designing each one.
